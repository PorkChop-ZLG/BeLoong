## 一、三层魔改架构

『化龍』对 DS 的魔改**不是单一手段**，而是三层叠加。理解三层分工是读懂后续所有内容的前提。

```
┌─────────────────────────────────────────────────────────────────────┐
│ 第 1 层：KubeJS 数据包覆盖                                            │
│   kubejs/data/<ns>/<与模组同名路径>  → 整体覆盖                       │
│   手段：纯 JSON，零代码，热重载友好                                    │
│   能做：物种 / 技能 / 阶段 / 诅咒 / 身体 / 表情 / 饮食 / 信标 / 末地平台 / 标签 │
│   不能做：新增注册表条目类型、新增属性、新增效果类型、改运行逻辑         │
├─────────────────────────────────────────────────────────────────────┤
│ 第 2 层：化龙核心模组 BeLoong-Core（Java + Mixin）                    │
│   ① Mixin：注入属性、改写运行公式、修模组缺陷                          │
│   ② 注册自定义能力效果类型：beloong:air_strike / beloong:tp_loong_palace│
│   ③ 自带数据包内容：dragonsurvival:air_strike 等技能 JSON              │
│   ④ 注册自定义状态效果：flight_ban / serene / growth_acceleration 等   │
├─────────────────────────────────────────────────────────────────────┤
│ 第 3 层：KubeJS 脚本（startup_scripts / server_scripts）               │
│   手段：注册自定义物品、批量改物品属性、右键交互                        │
│   例：kubejs:cave_dragon_heart 等"龙心"系列、配方改写                  │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.1 分层判据：不是「数据 vs 代码」，而是「能否扩展注册表」

第 2 层里也有大量**数据包内容**（`BeLoong-Core/src/main/resources/data/`）。
它们之所以放在模组里而不是 KubeJS，是因为**引用了只有模组才能注册的东西**：
自定义 `effect_type`、自定义 `mob_effect`、自定义 `attribute`、自定义 `damage_type`。
反过来，只要不引用自定义注册项，就应放第 1 层（可热重载、无需重新编译打包）。

**实操判据**：

> 技能 JSON 里出现 `"effect_type": "beloong:xxx"` ⇒ 放核心模组；
> 只用 `dragonsurvival:*` / `minecraft:*` ⇒ 放 KubeJS。

**排错判据**：当你在数据包 JSON 里看到某个注册表 ID 在模组里"查不到"时，
**先去第 2 层（核心模组）找**，不要立刻判定为笔误。

### 1.2 「覆盖 = 整体重写」的源码依据

DS 的 7 个 datapack registry **全部使用两参数重载**，不携带 `Cookie`：

```java
// DragonSpecies.java:110 / DragonAbility.java:172 / DragonBody.java:221
// DragonEmoteSet.java:32 / DragonPenalty.java:112 / DragonStage.java:163 / ProjectileData.java:44
event.dataPackRegistry(REGISTRY, DIRECT_CODEC, DIRECT_CODEC);
```

两参数重载**不携带 `Cookie`** ⇒ NeoForge **不做对象级合并**，
而是用 `DIRECT_CODEC` 把高优先级包里的整个 JSON 解析为该 id 的最终值。

⇒ **覆盖 = 完整重写该文件，没有字段级 merge。**

这条推论解释了两个看似矛盾的现象：

1. `cave_dragon.json` 覆盖版必须**原样抄回** `misc_resources` 全部内容，只加/改需要的字段；
2. 附属从龙的覆盖版是**附属原始文件 + 增量字段的并集**，不是只写增量。

## 二、源码验证过的数据结构

以下字段表均从 DS 2.0.69 的 `DIRECT_CODEC` 定义读出。**这是本文最可直接查阅的部分。**

### 2.1 `dragon_species` — `DragonSpecies.java:45-54`

```java
starting_growth             // Optional，doubleRange(1, MAX)
unlockable_behavior         // Optional
mana_handling               // Optional，默认 ManaHandling.DEFAULT
custom_stage_progression    // Optional<HolderSet<DragonStage>>
bodies                      // Optional<HolderSet<DragonBody>>，默认 empty
abilities                   // Optional<HolderSet<DragonAbility>>，默认 empty
penalties                   // Optional<HolderSet<DragonPenalty>>，默认 empty
misc_resources              // 必需
```

**没有** `growth` / `stages` / `start_stage` 字段 —— 起始阶段由 `starting_growth` 反查。

`abilities` / `penalties` / `bodies` 走 `RegistryCodecs.homogeneousList(...)`，
因此**既接受数组，也接受 `#标签` 引用字符串**。项目统一用标签引用：

```json
{ "abilities": "#dragonsurvival:cave_dragon", "penalties": "#dragonsurvival:cave_dragon" }
```

#### `mana_handling` 的双层默认值（极易踩）

| 写法 | 结果 |
|---|---|
| 完全没有 `mana_handling` 键 | `ManaHandling.DEFAULT = (xp 0.1, perLevel 0.25, max 9)` |
| 写了 `"mana_handling": {}` | 三字段各取 codec 默认 → **(0, 0, 0)**，等于**关闭** |

项目统一用 `{ "mana_per_level": 0.2, "mana_xp_conversion": 0, "max_mana_from_levels": 20 }`。

> 据既有文档（`ManaHandler.java:119-129`）：`mana_per_level` 乘的是 **`player.experienceLevel`（原版经验等级）**，
> 不是龙成长等级、也不是能力等级。故 `{0.2, 0, 20}` 的真实含义是
> **每 1 个原版经验等级 +0.2 最大魔力，最多 +20（即经验等级 100 封顶），并关闭 XP↔魔力互转**。

#### `unlockable_behavior` 的解锁条件

`unlock_condition` 就是原版 `LootItemCondition.DIRECT_CODEC`。
项目的标准写法是 `any_of` 双分支，保证跳过教程的玩家也能解锁
（**按准则 §2.0 原则 4，`condition` 值必须写全 `minecraft:` 前缀**）：

```json
{
  "visibility": "visible_if_locked",
  "unlock_condition": {
    "condition": "minecraft:any_of",
    "terms": [
      { "condition": "minecraft:entity_properties", "entity": "this",
        "predicate": { "type_specific": { "type": "player",
          "advancements": { "beloong:beloong/finish_beginner_tutorial": true } } } },
      { "condition": "minecraft:entity_properties", "entity": "this",
        "predicate": { "type_specific": { "type": "player",
          "advancements": { "beloong:beloong/skip_beginner_tutorial": true } } } }
    ]
  }
}
```

> ⚠️ **历史遗留**：项目现有的 `cave_dragon.json` / `dihuang_loong.json` 覆盖版仍省略前缀
> （`annihilator` / `frostfire` 已写全）。省略可正常工作，但**不符合现行规范**；
> 触及这些文件时应顺手补全，但不要为补前缀而单独做无谓的整体改动。

### 2.2 `dragon_ability` — `DragonAbility.java:55-62`

顶层**只有 6 个字段**：

```java
activation                  // 必需，dispatch 字段 activation_type
upgrade                     // Optional，dispatch 字段 upgrade_type
usage_blocked               // Optional<LootItemCondition>
actions                     // Optional，默认 []
can_be_manually_disabled    // 默认 true
icon                        // 必需，LevelBasedResource
```

**顶层没有** `mana_cost` / `cooldown` / `range` / `duration` / `effect_type`：

- `mana_cost` / `cooldown` / `cast_time` 在 **`activation` 内部**（`initial_mana_cost` / `continuous_mana_cost`）
- `effect_type` 是 `actions[].target_selection.applied_effects.entity_effect[]` 元素的 dispatch 字段
- `target_type` 在 `target_selection` 内：`self` / `area` / `disc` / `looking_at` / `dragon_breath`

#### `upgrade_type` 取值与 `maximum_level` 的对应

| `upgrade_type` | 是否需 `maximum_level` | 等级上限来源 |
|---|---|---|
| `dragonsurvival:experience_points` | **需要** | 字段值 |
| `dragonsurvival:experience_levels` | **需要** | 字段值 |
| `dragonsurvival:dragon_growth` | **需要** | 字段值 |
| `dragonsurvival:item_based` | 无 | `items_per_level.size()` |
| `dragonsurvival:condition_based` | 无 | `conditions.size()` |

> 项目的 `*_wings.json` 用 `dragon_growth` + `maximum_level: 6`；
> 而 DS 原版 `cave_wings.json` 用 `condition_based`（只有 0/1 两态）—— **项目是刻意改写的**。

#### 等级下界：`DragonAbilityInstance.MIN_LEVEL_FOR_CALCULATIONS = 1`

`DragonAbilityInstance.java:44` 定义了权威的等级下界 `1`。
三个 upgrade 实现（`DragonGrowthUpgrade:28` / `ExperienceLevelUpgrade:28` / `ConditionUpgrade:36`）
**都从这个常量起循环**，而不是硬编码 `1`。

#### 等级 → 成长的换算（`DragonGrowthUpgrade.java:26-34`）

```java
int newLevel = 0;
for (int level = MIN_LEVEL_FOR_CALCULATIONS; level <= maxLevel(); level++) {
    if (data.input() < growthRequirement.calculate(level)) break;
    newLevel++;
}
```

⇒ 等级 N = 满足 `growth >= requirement(N)` 的最大 N；`growth < requirement(1)` 时为 0 级。

### 2.3 `dragon_stage` — `DragonStage.java:52-60`

```java
is_default                    // bool，默认 false
growth_range {min, max}       // 必需，min >= 1 且 max > min
ticks_until_grown             // 必需，intRange(1, daysToTicks(365))
modifiers                     // 默认 []
growth_items                  // 默认 []
is_natural_growth_stopped     // Optional<EntityPredicate>
destruction_data              // Optional
```

**没有 `next_stage` 字段** —— 阶段链靠 `growth_range` 数值**首尾相接**（`areStagesConnected`），
边界值归下一个阶段。

#### 会被强校验、配错直接崩启动的两处

1. **三阶段必须存在**（`DragonStage.validate:84-86`）：`newborn` / `young` / `adult` 三个 id 必须存在。
2. **区间必须连续**（`:120`）：默认阶段区间不连续 → `IllegalStateException`。
   同理 `DragonSpecies.validate:96-101` 会对每个设了 `custom_stage_progression` 的物种
   调用 `areStagesConnected`，**区间不连续直接崩游戏启动**。
3. **`destruction_data` 必须落在本阶段区间内**（`:103` / `:108`）：
   `block_destruction_growth` 与 `crushing_growth` 越界 → 校验失败。

#### `growth_items` 的字段

```java
items               // id 列表 或 #tag
growth_in_ticks     // int，可为负；0 = 切换自然成长开关
maximum_usages      // 默认 -1 = 无限
```

### 2.5 `Modifier`（数值提供器）— `Modifier.java:17-21`

**这是整套系统的地基。** 所有 `amount` / `growth_requirement` / `duration` / `amplifier` 都用它。

```java
attribute   // Attribute.CODEC
amount      // either(LevelBasedValue.CODEC, PreciseLevelBasedValue.CODEC)
operation   // AttributeModifier.Operation.CODEC
```

- `LevelBasedValue` 是**原版**的 `BuiltInRegistries.ENCHANTMENT_LEVEL_BASED_VALUE_TYPE`，不是 DS 自定义。
- 可用 `type`：`minecraft:linear` / `minecraft:lookup` / `minecraft:clamped` / `minecraft:fraction` / `minecraft:levels_squared`；
  **裸数字 = Constant**。
- `lookup`：`calculate(level) = level <= values.size() ? values.get(level-1) : fallback.calculate(level)`
  —— `fallback` 是**必需字段**，仅在 level 超出 `values` 长度时启用。
- `linear`：`calculate(level) = base + per_level_above_first * (level - 1)`，**第 1 级取 `base`**。
- DS **额外**支持 `PreciseLevelBasedValue`（`Modifier.java:23-32`）：
  `{"precise_base": B, "precise_amount": A}` → `B + A * level`，**double 连续值，不截断**。

#### ⚠️ 两个 `calculate` 的语义差异（易错）

```java
// Modifier.java:59-61
public double calculate(double level) {
    return amount.map(value -> (double) value.calculate((int) level),   // LevelBasedValue：截断成 int
                       value -> value.calculate(level));                 // PreciseLevelBasedValue：保留 double
}
```

| 类型 | 公式 | 等级语义 |
|---|---|---|
| `linear` (LevelBasedValue) | `base + per_level_above_first * (level - 1)` | **第 1 级取 base** |
| `precise_*` (PreciseLevelBasedValue) | `base + amount * level` | **level 不减 1**，且不截断 |

这解释了为什么项目里 `dragon_stage` 的 `generic.scale` 全用 `precise_*`
（需要连续缩放），而 `max_health` / `attack_damage` 用 `linear`。

### 2.6 `DietEntry` — `DietEntry.java:24-29`

```java

properties        // Optional<FoodProperties>（原版 FoodProperties.DIRECT_CODEC）
retain_effects    // Optional<Either<Boolean, RetainEffects>>
```

> ⚠️ **`nutrition` / `saturation` / `eat_seconds` / `can_always_eat` / `effects` / `using_converts_to`
> 都不是顶层字段**，全部嵌在 `properties` 里，由**原版** `FoodProperties.DIRECT_CODEC` 定义。

`properties` 内字段（原版 `FoodProperties`）：

| 字段 | 类型 | 必需/默认 |
|---|---|---|
| `nutrition` | 非负 int | **必需** |
| `saturation` | float | **必需** |
| `can_always_eat` | bool | 默认 `false` |
| `eat_seconds` | 正 float | 默认 `1.6` |
| `using_converts_to` | 单物品 | 可选 |
| `effects` | `List<PossibleEffect>` | 默认 `[]`，元素 `{effect, probability=1}` |

#### `retain_effects`：2.0.70 的增强能力

`RetainEffects`（`DietEntry.java:118-132`）是 `{beneficial, neutral, harmful}` 三个 bool，
按**效果类别**决定是否保留原物品的进食效果：

```java
public boolean retain(final MobEffectInstance effect) {
    return switch (effect.getEffect().value().getCategory()) {
        case BENEFICIAL -> beneficial;
        case HARMFUL -> harmful;
        case NEUTRAL -> neutral;
    };
}
```

也可写 `"retain_effects": true`（`Either.left(true)`，全部保留）。
这比旧版只能"整体保留 / 整体丢弃"精细得多。

#### `items` 的三种写法

`namespace:path` / `#tag` / **正则**（合法起始字符：`. ^ [ ( \`）。
项目 `item_blacklist` 用到了正则：

```json
"items": ["#c:tools/shield", "minecraft:trident", ".*:.*?elytra.*", "cataclysm:black_steel_targe", ...]
```

#### ⚠️ 覆盖语义：`DietEntry.equals` 只比较 `items` 字符串

```java
// DietEntry.java:100-111
public boolean equals(final Object other) {
    if (!(other instanceof DietEntry otherDiet)) return false;
    return this.items.equals(otherDiet.items());   // 只比 items
}
```

⇒ 想**替换**某条必须**逐字保持 `items` 字符串一致**（含 `#tag` 前缀与正则原文），
否则会变成"新增一条"而不是"覆盖"。

## 三、项目实际使用的六类手法

### 手法 1：物种覆盖 + 双重解锁条件

`kubejs/data/dragonsurvival/dragonsurvival/dragon_species/cave_dragon.json` 是**完整重写**，
改动只有两处：加 `mana_handling`、加 `unlockable_behavior`，其余（含 `misc_resources` 全部贴图路径）原样保留。

这是 §1.2「覆盖 = 整体重写」的直接体现。

### 手法 2：成长链拉长 —— 20 → 300 的连续六阶段

**这是适配新从龙最容易漏的一步。**

DS 默认三阶段的成长上限只有 **60**（`newborn 10-25` / `young 25-40` / `adult 40-60`），
而 6 级翅膀需要 `growth_requirement` 达到 **250**。
⇒ 只改技能不改阶段，3 级以上永远不可达；只改阶段不改技能，成长经验被浪费。**两者必须联动。**

项目实际区间（`kubejs/data/dragonsurvival/dragonsurvival/dragon_stage/`）：

| 阶段 | `growth_range` | 性质 |
|---|---|---|
| `newborn` | 20 – 50 | 覆盖（原 10–25） |
| `young` | 50 – 100 | 覆盖（原 25–40） |
| `adult` | 100 – 150 | 覆盖（原 40–60） |
| `cave_ancient` | 150 – 200 | **新增** |
| `cave_archean` | 200 – 250 | **新增** |
| `cave_progenitor` | 250 – 300 | **新增** |

首尾严格相接（50/50、100/100、150/150、200/200、250/250），否则触发 §2.3 的连接性校验崩启动。

### 手法 3：六段式翅膀技能

项目对**全部 `*_wings` 技能**统一施加三段 modifier + 6 级 + 贴图复制。
以 `cave_wings.json` 为实例（结构已核对）：

```jsonc
{
  "actions": [{
    "target_selection": {
      "target_type": "dragonsurvival:self",
      "applied_effects": {
        "targeting_mode": "allies_and_self",
        "entity_effect": [
          // ① 能不能飞
          { "effect_type": "dragonsurvival:flight",
            "icon": "dragonsurvival:textures/ability_effect/cave_dragon_wings.png",
            "level_requirement": 1 },

          // ② 飞行等级阶梯（0..5）
          { "effect_type": "dragonsurvival:modifier",
            "modifiers": [{
              "base": { "id": "dragonsurvival:cave_wings_flight_level", "is_hidden": true },
              "modifiers": [{
                "attribute": "dragonsurvival:flight_level",
                "amount": { "type": "minecraft:lookup", "values": [0,1,2,3,4,5],
                            "fallback": { "type": "minecraft:linear", "base": 0.0, "per_level_above_first": 1.0 } },
                "operation": "add_value" }]}]},

          // ③ 飞行速度：-0.2 起，每级 +0.1
          { "effect_type": "dragonsurvival:modifier",
            "modifiers": [{ "base": { "id": "dragonsurvival:cave_wings_flight_speed", "is_hidden": true },
              "modifiers": [{ "attribute": "dragonsurvival:flight_speed",
                "amount": { "type": "minecraft:linear", "base": -0.2, "per_level_above_first": 0.1 },
                "operation": "add_value" }]}]},

          // ④ 飞行耐力：同上
          { "effect_type": "dragonsurvival:modifier",
            "modifiers": [{ "base": { "id": "dragonsurvival:cave_wings_flight_stamina", "is_hidden": true },
              "modifiers": [{ "attribute": "dragonsurvival:flight_stamina",
                "amount": { "type": "minecraft:linear", "base": -0.2, "per_level_above_first": 0.1 },
                "operation": "add_value" }]}]}
        ]
      }
    }
  }],
  "activation": { "activation_type": "dragonsurvival:passive" },
  "icon": { "texture_entries": [
    { "from_level": 0, "texture_resource": "dragonsurvival:abilities/cave/cave_wings_0" },
    { "from_level": 1, "texture_resource": "dragonsurvival:abilities/cave/cave_wings_1" },
    // from_level 2..6 全部指向 cave_wings_1
  ]},
  "upgrade": {
    "upgrade_type": "dragonsurvival:dragon_growth",
    "maximum_level": 6,
    "growth_requirement": { "type": "minecraft:lookup",
      "values": [20, 50, 100, 150, 200, 250],
      "fallback": { "type": "minecraft:linear", "base": 20.0, "per_level_above_first": 50.0 } }
  }
}
```

#### `lookup` 的等级从 1 起算 —— 三档语义

| 能力等级 | `flight_level` | 效果 |
|---|---|---|
| 0（未学习） | base `0.0` | —— |
| 1（幼龙） | 0 | 可飞，**不可**稳定悬停 |
| 2（成年） | 1 | 可飞 + **稳定悬停** |
| 3 ~ 5 | 2 ~ 4 | —— |
| 6（满级） | 5 | —— |

> `values[0] = 0.0` 对应的是**能力等级 1**，不是"0 级"。
> 因为 `LevelBasedValue` 的 level 参数从 1 起算，而 modifier 只在能力等级 ≥ 1 时生效。

> `flight_level` 的**三档语义**（据既有文档，属性由 BeLoong-Core 注入）：
> `< 0` 禁止展翅 / `= 0` 可飞不能悬停 / `>= 1` 可飞 + 稳定悬停。

#### `base.is_hidden: true` 的作用

`ModifierWithDuration` 的 `base` 字段类型是 `DurationInstanceBase`
（含 `id` / `duration` / `should_remove_automatically` / `early_removal_condition` / `custom_icon` / `is_hidden`）。
`is_hidden: true` 让这条修正**不出现在技能 tooltip 的属性列表里**，避免把"飞行等级 0~5"这种内部数值暴露给玩家。

#### `flight_speed` / `flight_stamina` 的语义易误读

DS 里这两个属性的**注册 base 是 1**，`base: -0.2` 是**这条 modifier 自身的基线**：

```
最终值 = 属性 base(1) + Σ(add_value 修正)
```

- 能力等级 1（`linear` 在 level=1 取 `base`）→ `1 + (-0.2) = 0.8`（比无修正**慢**）
- 能力等级 6 → `1 + (-0.2 + 0.1 × 5) = 1.3`

`flight_stamina` 是**除数**（`drain /= stamina`），越大越省力。
⇒ 1 级时飞行更费饥饿、6 级时更省。

#### 关于 `id` 复用

项目所有翅膀技能都复用 `id: dragonsurvival:cave_wings_flight_*`（连附属的 `annihilator_type_wings.json` 也照抄）。
这是安全的：同一玩家同一时刻只可能是一条龙种，属性修饰符按 id 去重不会互相干扰。

### 手法 5：标签 —— 追加 vs 替换

| 场景 | 写法 | 项目实例 |
|---|---|---|
| 给模组已有标签**追加**条目 | 不写 `replace`（默认 `false`） | `tags/dragonsurvival/dragon_ability/cave_dragon.json` |
| **替换**模组标签 | `"replace": true` | `tags/dragonsurvival/dragon_species/order.json`、`dragon_penalty/dihuang_loong.json` |
| 新增自制标签 | `"replace": false` | `tags/dragonsurvival/dragon_ability/annihilator_type_a.json` |

#### 各标签的运行时语义（据既有文档）

- `dragon_species/order.json` → **祭坛物种显示顺序**（`DragonAltarScreen`），
  按 tag 索引排序，**不在 tag 中的物种排最后**。
  `beginner_aether_dragon` 必须在最底部是玩法引导需求。
- `dragon_ability/order.json` → **能力界面三列排序**（主动 / 可升级被动 / 恒定被动）。

项目当前 `dragon_species/order.json`（`replace: true`，14 项）：

```json
["dragonsurvival:aether_dragon", "dragonsurvival:dihuang_loong", "dragonsurvival:cave_dragon",
 "dragonsurvival:forest_dragon", "dragonsurvival:sea_dragon", "dragonsurvival:tundra_dragon",
 "star_dragon:star_dragon", "dragonsurvival:neo_crystcursed_dragon", "dragonsurvival:astral_dragon",
 "dragonsurvival:frostfire_dragon", "dragonsurvival:wing_kirin", "dragonsurvival:annihilator_type_a",
 "dragonsurvival:night_striker", "dragonsurvival:beginner_aether_dragon"]
```

#### ⚠️ `dragon_ability/<物种>.json` 的唯一失败模式

```json
{ "values": ["dragonsurvival:become_bigger", "dragonsurvival:become_smaller"] }
```

**必须保持 `replace: false`（即省略该字段）**。标签默认是**追加**语义，模组自带条目与本文件会**合并**，
所以只写增量即可。一旦误写成 `"replace": true`，本文件会**清空模组累积的全部技能**，
该物种将只剩这两个通用技能。

> 注：项目实际文件中 `cave_dragon.json` 抄写了模组原有 17 条 + 追加 2 条（共 19 条），
> 而非准则 §2.2.3 建议的"只写 2 条增量"。两种写法**结果等价**（只要 `replace` 不为 `true`），
> 前者更抗模组更新带来的列表变化，后者更短。

## 四、耦合与陷阱

### 4.1 DataMap 覆盖丢失了 `neoforge:conditions` 守卫

**已核实的格式差异**（此处修正既有文档 §4.4 的描述）：

| | 模组原版 | 化龙覆盖版 |
|---|---|---|
| 外层 `"values"` 包装 | **有** | **有**（保留） |
| 每物种的 `neoforge:conditions` | 有 | **已删除** |
| 每物种的 `neoforge:value` | 有（值嵌在里面） | **已删除**，值直接提到物种键下 |

模组原版（`src/generated/resources/data/.../diet_entries.json`）：

```jsonc
{ "values": {
    "dragonsurvival:cave_dragon": {
      "neoforge:conditions": [{ "type": "dragonsurvival:registered",
        "registry": "dragonsurvival:dragon_species", "value": "dragonsurvival:cave_dragon" }],
      "neoforge:value": [ { "items": "#minecraft:coals", "properties": {...} }, ... ] } } }
```

化龙覆盖版（`kubejs/data/dragonsurvival/data_maps/.../diet_entries.json`）：

```jsonc
{ "values": {
    "dragonsurvival:cave_dragon": [ { "items": "#minecraft:coals", "properties": {...} }, ... ] } }
```

⚠️ 注意：**外层 `"values"` 包装必须保留**，被去掉的只是条件与 `neoforge:value` 这一层。
`dragon_beacon_data.json` 还保留了 `#dragonsurvival:all` 作为**兜底条目**（`values` 的第一个键），
再为每个物种追加专属效果。

**收益**：文件更短、可读性更好，且省去了 datagen 专属条件。
**代价**：条目失去了"该物种 / 依赖模组是否已注册"的守卫。

⇒ 这 5 个 DataMap 文件（`body_icons` / `diet_entries` / `dragon_beacon_data` / `end_platforms` / `stage_resources`）
**引用了所有龙之生存附属模组的物种 id 与物品 id**
（`star_dragon:*`、`tundradragon:*`、`frostfire_dragon:*`、`crystcursed_dragon:*`、`ds_aether_addon:*`、`wing_kirin:*` 等）。

> **这 5 个文件是全附属模组的硬依赖集合**。任何附属被移除，对应的物种 id / 物品 id 立即悬空。
> 改动或精简整合包模组列表时，**必须同步清理这 5 个文件**。

### 4.2 `beloong` 核心模组是硬前置依赖

数据包里 12 个 `*_wings` 技能引用的 `dragonsurvival:flight_level` 属性
**不在 DS 里**，而是 `beloong` 核心模组注入的。
⇒ 移除核心模组会让这 12 个文件全部解析失败。同理 `beloong:mana_loss` / `beloong:serene` 等自定义效果。

### 4.3 0 级 tooltip 的历史问题（2.0.70 已由 DS 自行修复）

DS 在渲染**未学习技能**的 Modifier 描述时会传入等级 0，
而 `LevelBasedValue.Lookup` 会执行 `values.get(-1)` ⇒ **数组越界崩溃**。

现在 DS 自己有了防护（`LevelBasedValueMixin.java:21-26`）：

```java
@Inject(method = "calculate", at = @At("HEAD"), cancellable = true)
private void dragonSurvival$skipLevelZero(final int level, final CallbackInfoReturnable<Float> callback) {
    if (level == 0 && DragonSurvival.PROXY.shouldGuardLevelBasedLookup()) {
        callback.setReturnValue(fallback.calculate(level));   // 走 fallback，不崩
    }
}
```

且这个开关**只在 tooltip 渲染窗口内**打开（`DragonAbility.java:103` 开 / `:142` 关），
源码注释明确说明意图：「不总是开，这样数据包等仍能收到非法配置的报错」。

⇒ 给技能写 `lookup` 型 `amount` 时，**0 级安全问题现在由 DS 官方兜底**，
但前提是 **`fallback` 写得正确**（它就是 0 级时被 `calculate` 的值）。

## 五、相对既有文档的修正

`docs/plans/2026-09-13-dragonsurvival-kubejs-modding-guide.md` 的大框架仍然正确，
以下 4 处需按本文更新：

### ① §5.4「`ModifierMixin` 修 tooltip 的 0 级数组越界」→ 已降级为冗余保险

```java
for (int level = DragonAbilityInstance.MIN_LEVEL_FOR_CALCULATIONS; level <= maxLevel(); level++)
```

语义相同，但引用常量更稳。

```java
MiscCodecs.conditional(LootItemCondition.DIRECT_CODEC).optionalFieldOf("usage_blocked")           // :58
```

## 六、适配新从龙的检查清单

按顺序核对（★ 为最易漏项）：

1. **确定命名空间形态**
   - 标准：物种 id 在 `dragonsurvival` 下，资源也在 `dragonsurvival` 下
   - 独立：如 `star_dragon:star_dragon`，数据与资源都用自己的命名空间
   - 混合：物种 id 在 `dragonsurvival` 下，资源 / 技能贴图用附属自己的命名空间（如 `annihilator_type_a`）
2. **完整重写** `dragon_species/<id>.json`（抄全原文件 + 追加 `mana_handling` + `unlockable_behavior`）
3. ★ **确认成长上限 ≥ 最高技能等级需求**（6 级翅膀需 250），必要时改 `custom_stage_progression` 与 `dragon_stage` 区间
4. **改写 `*_wings.json`**：三段 modifier（`flight_level` lookup + `flight_speed` / `flight_stamina` linear）+ 6 级 + 贴图复制
   - 确认 `beloong` 核心模组在位，否则 `dragonsurvival:flight_level` 属性不存在
   - 确认所有 `lookup` 都写了正确的 `fallback`
5. **`diet_entries.json`**：追加通用食物 + 附属专属食物；注意 `saturation ≤ nutrition`（否则被 `FoodData.add()` 截断）
6. **`dragon_beacon_data.json`**：2~3 个效果，**必含 `dragonsurvival:empowered_soul`**
7. **`end_platforms.json`**：坐标与其他物种**不重叠**（按 structure id 判重），复用平台时同时复用坐标
8. **`stage_resources.json`**：若附属未提供独立贴图，需新增该物种条目
9. **`dragon_ability/<物种>.json`**：`replace` 必须为 `false`（省略）
10. **`dragon_species/order.json`**：插入合适位置，`beginner_aether_dragon` 保持最底
11. **语言文件**：中英各补齐 4 个键（主键 / `.locked` / `.altar.desc` / `.banner.desc`），格式见准则 §2.1.1
12. **判断技能归属**：`effect_type` 只用 `dragonsurvival:*` / `minecraft:*` → KubeJS；含 `beloong:*` → 核心模组
13. **实机验收**：祭坛可见性与解锁条件、成长到满级、翅膀 6 级（含悬停何时解锁）、
    信标效果（付费与记忆方块两种模式）、末地平台、饮食 GUI、诅咒提示

### 修改原则（准则 §2.0 重申）

1. **尊重整合包原文件格式**：不要用工具整体重排 / 格式化 JSON
2. **最小修改**：只在文件**尾部**追加，尽量不改已有条目
3. **Tab 缩进一致**：底部条目用什么缩进，新增就用什么；不要混用空格与 Tab
4. **原版 `condition` 必须写全 `minecraft:` 前缀**：使用原版 `LootItemCondition`
   （`location_check` / `entity_properties` / `inverted` / `any_of` / `all_of` / `value_check` 等）时，
   值必须写成 `minecraft:xxx`，**不允许省略**。
   - 省略虽能靠 `ResourceLocation` 默认补全而正常工作，但会让「原版条件」与「模组条件」在字面上无法区分
   - ✅ `"condition": "minecraft:location_check"`　❌ `"condition": "location_check"`
   - 模组条件本身就必须带命名空间（如 `dragonsurvival:registered`），不受此条影响
   - 只管 `condition` **字段的值**；`item` / `block` / `effect` / `dimension` 等注册项 id 本就应写全

## 七、可复用的操作方法

### 7.1 判定「覆盖模组」还是「化龙新增」

```powershell
$ov = 'kubejs\data\dragonsurvival\dragonsurvival'   # 路径含全角括号时用 -like 在 PowerShell 侧过滤
$md = 'D:\Minecraft\开源模组参考文件\DragonSurvival\src\generated\resources\data\dragonsurvival\dragonsurvival'
foreach ($sub in 'dragon_ability','dragon_species','dragon_stage','dragon_penalty','dragon_body') {
  Get-ChildItem "$ov\$sub" -File -Filter *.json -ErrorAction SilentlyContinue | ForEach-Object {
    $s = if (Test-Path -LiteralPath "$md\$sub\$($_.Name)") { '覆盖模组' } else { '化龙新增' }
    "$sub/$($_.Name)  $s"
  }
}
```

> 判定"是否覆盖模组"时，除 DS 本体外，还要把**各附属模组的 jar** 一并作为比对基准
> —— 13 个从龙的物种文件其实覆盖的是各附属 mod。
> 核心模组 `BeLoong-Core` 的 `src/main/resources/data/` 也要纳入比对范围。

### 7.2 权威数据源必须是 jar，不是解压目录

DS 打包的 JSON 在 `mods\[龙之生存] DragonSurvival-*.jar` 内。
解压目录不保证与 jar 同步，**凡"某文件是否存在"的判定一律对 jar 做检查**：

```powershell
Add-Type -AssemblyName System.IO.Compression.FileSystem
$z = [System.IO.Compression.ZipFile]::OpenRead($jarPath)
$e = $z.GetEntry('data/dragonsurvival/dragonsurvival/dragon_ability/cave_wings.json')
$sr = New-Object System.IO.StreamReader($e.Open()); $sr.ReadToEnd(); $sr.Close(); $z.Dispose()
```

## 八、设计精要：为什么三层架构是必要的

整套魔改里设计最精巧的一环是 **`flight_level` 的三档语义 + `beloong:flight_ban` 的数值博弈**
（据既有文档，核心模组 0.9.3 Javadoc）：

```
数据包：翅膀能力等级 1..6  →  flight_level 0..5   （lookup 阶梯）
核心模组：beloong:flight_ban  每级 -1.0 飞行等级   （vanilla 按 amount × (amplifier+1) 自动缩放）

结果：
  禁空 I（amp 0）→ flight_level -1
  翅膀技能 2 级（成年龙）+1 飞行等级  →  恰好抵消 1 级禁空
```

与 DS 原生 `BROKEN_WINGS` 的区别：`BROKEN_WINGS` 无条件强制收翅；
`flight_ban` 只在飞行等级降至负数时才收翅，从而保留
**"低等级禁空只能削弱悬停、不能阻止飞行"的梯度**。

⇒ `flight_level` 成为一个**独立于能力等级、可被外部削弱的量**，
使"敌方禁空 vs 玩家升级翅膀反制"形成可对抗的数值博弈。

**这套设计完全无法用纯数据包实现** —— 需要注册新属性（`flight_level`）与新状态效果（`flight_ban`），
而这只能由模组层完成。这正是第 2 层存在的根本理由。
